1Build and install (Windows)

hashstash is two programs: hs, the client you use in a project, and hshub, the server. Both build from source with a C++20 compiler. Every library is downloaded automatically by CMake.

On a fresh Windows install

  1. Install the tools (PowerShell). WinLibs includes the GCC compiler and Ninja: 
    PS> winget install Git.Git Kitware.CMake Python.Python.3.13 BrechtSanders.WinLibs.POSIX.UCRT
PS> python -m pip install pytest
    Open a new terminal afterwards so the tools are on PATH. Check them with g++ --version, cmake --version and ninja --version.
  2. Get the source and build: 
    PS> git clone https://github.com/richapma78/hashstash.git C:\Projects\hashstash
PS> cd C:\Projects\hashstash
PS> cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release
PS> cmake --build build
    The first build downloads SQLite, tree-sitter, BLAKE3 and the other libraries, and takes a few minutes.
  3. Run the tests: 
    PS> build\hs_tests.exe
...
70 checks passed, 0 failed
  4. Put C:\Projects\hashstash\build on your PATH so hs and hshub work from any folder: 
    PS> [Environment]::SetEnvironmentVariable("Path", $env:Path + ";C:\Projects\hashstash\build", "User")
The executables are statically linked, so hs.exe and hshub.exe can be copied to another Windows machine on their own. Python and pytest are only needed for running Python tests.

2Your first project

The examples use a small project with one module and its tests:

sample_project/
  calc/__init__.py
  calc/ops.py          add, mul, class Calculator (__init__, apply, clear)
  tests/test_ops.py    test_add, test_add_negative, test_mul, TestCalculator.test_apply

Create a store and import the code. The store is the .hs/ folder in the project directory.

> mkdir calc-work && cd calc-work
> hs init calc
Created hashstash project 'calc' in C:/…/calc-work/.hs
> hs import C:\Projects\hashstash\tests\fixtures\sample_project
Imported 3 source files (11 definitions) and 0 other files.
Linked 4 tests to the definitions they call.
  2 functions/methods have no test cases (hs tests missing).

Import split the files into definitions, built the index and call graph, and linked each test to the functions it calls. Nothing is committed yet:

> hs status
On branch main (no commits yet)
Uncommitted changes:
  new file      calc/__init__.py
  new file      calc/ops.py
  new file      tests/test_ops.py
  added         calc/ops.py:add
  added         calc/ops.py:mul
  …
  test links changed
> hs commit -m "Import the calc sample"
Committed #b5dpcitcko on main
  …
Not verified yet: run hs verify before pushing.

To get ordinary files back at any time:

> hs render --out ..\calc-out
Rendered to C:/…/calc-out: 3 written, 0 unchanged, 0 deleted.
> cd ..\calc-out && python -m pytest -q
....                                                                     [100%]
4 passed in 0.01s
Names. Definitions are named file:Class.method, e.g. calc/ops.py:Calculator.apply. A unique short form works too: add, Calculator.apply. A repeated name in the same scope gets ~2, ~3…

4Editing

Code lives in the store, so you don't edit files directly. hs edit locks the definitions and writes them to a scratch file in .hs/scratch/. Open it in any editor:

> hs edit calc/ops.py:mul
Opened for editing in C:/…/calc-work/.hs/scratch/edit.py
Locked for 15 minutes (renewed as you work). When done: hs update

The scratch file looks like this. Change the code below the # @hs: line and leave that line alone:

# hashstash scratch file. Edit the definitions below, then run: hs update
# Each section starts with a "# @hs:" line; keep those lines as they are.
# A section may hold several definitions (e.g. a function split into helpers).
# Add code:     # @hs:new <file>[:<Class>] [after=<name>]
# Delete code:  # @hs:delete <file>:<name>

# @hs:edit calc/ops.py:mul base=5xp6l2zxot
def mul(a, b):
    """Multiply a by a non-negative integer b."""
    if b < 0:
        raise ValueError("b must be non-negative")
    total = 0
    for _ in range(b):
        total = add(total, a)
    return total

Store the edit with a reason, review it, and commit:

> hs update -m "Reject negative b instead of silently returning 0"
stored  calc/ops.py:mul
> hs diff
  changed       calc/ops.py:mul
      @@ -1,4 +1,7 @@
       def mul(a, b):
      +    """Multiply a by a non-negative integer b."""
      +    if b < 0:
      +        raise ValueError("b must be non-negative")
           total = 0
           for _ in range(b):
               total = add(total, a)
> hs commit -m "mul: reject negative multipliers"
Committed #c4n53okjgb on main
  changed       calc/ops.py:mul
Released 1 lock(s).
Not verified yet: run hs verify before pushing.

Adding and deleting

  • hs new calc/ops.py opens a section for a new top-level function. hs new calc/ops.py:Calculator --after apply adds a method after apply.
  • hs rm calc/ops.py:Calculator.clear deletes a definition.
  • Renaming is just an edit: change def mul to def times. The lineage stays the same, so tests, notes and history follow the function.
The base= hash records which version you started from. If someone else changed the function in the meantime, hs update refuses instead of overwriting their work.

5Tests and verify

Linking tests to functions

Import links each test to the functions it calls. You can inspect and adjust the links yourself:

> hs tests calc/ops.py:add
calc/ops.py:add  #uo6gamhvxd  suite #3np2azwdey
  tests/test_ops.py:test_add  #7xdypxr7mu
  tests/test_ops.py:test_add_negative  #i5mbin3kmt
> hs tests missing
calc/ops.py:Calculator.__init__
calc/ops.py:Calculator.clear
2 definition(s) without test cases.
> hs tests suggest calc/ops.py:Calculator.clear     # tests that call it
> hs tests link calc/ops.py:Calculator.clear tests/test_ops.py:TestCalculator.test_apply
> hs tests autolink                                  # link suggestions wherever nothing is linked

A test for a method can create the whole class, or a higher-level object that uses it. Link it to every method it is meant to check.

Verify, then push

hs verify renders the working state to .hs/verify/tree and runs pytest on the tests that matter. Before the first push, that means everything:

> hs verify
  no tests                calc/ops.py:Calculator.__init__
  1/1 passed              calc/ops.py:Calculator.apply
  no tests                calc/ops.py:Calculator.clear
  2/2 passed              calc/ops.py:add
  1/1 passed              calc/ops.py:mul
  warning: calc/ops.py:Calculator.__init__: no test cases linked
  warning: calc/ops.py:Calculator.clear: no test cases linked
Verification passed (4 tests run).

Results come one line per function: how many of its tests passed. Individual tests are listed only when they fail (hs verify -v lists them all).

After that, verify checks only what the hub hasn't seen. After the mul edit, only its test runs:

> hs verify
  1/1 passed              calc/ops.py:mul
Verification passed (1 test run).

Impact testing

Verify also runs the tests of everything that calls what changed. Break add, and mul's test runs too:

> hs verify
  also testing callers: calc/ops.py:mul
  0/2 passed, 2 failed    calc/ops.py:add
  0/1 passed, 1 failed    calc/ops.py:mul
  FAIL  tests/test_ops.py:test_add
  FAIL  tests/test_ops.py:test_add_negative
  FAIL  tests/test_ops.py:test_mul
  failure: tests/test_ops.py:test_add: test failed
  …
Verification failed (3 tests run).
> hs push
hs: head #3thxoyazef is failing verification: run hs verify (it must pass) before pushing

Use hs verify --json to see each failing test's pytest output.

Test results per function

hs tests summary shows the whole project the same way, failing functions first. Add a file or name prefix to narrow it, and --problems to hide everything that passes:

> hs tests summary
  no tests                    calc/ops.py:Calculator.__init__
  no tests                    calc/ops.py:Calculator.clear
  1/1 passed                  calc/ops.py:Calculator.apply
  2/2 passed                  calc/ops.py:add
  1/1 passed                  calc/ops.py:mul
5 functions, 4/4 tests passed.

A function's numbers count only results on its current code and tests. The hub and every clone receive the results with each push and pull, so they all show the same numbers.

How tests are run.
  • Each test file runs from its own project root: the nearest folder with pytest.ini, pyproject.toml, setup.cfg or tox.ini, otherwise the folder above its package and its tests/ folder.
  • The command comes from [tests] python in the settings. Python bytecode caches are cleared first, so a test always runs the code being verified.
  • hs verify --all checks every definition.

6Reviewing changes

Every commit carries a review flag: unreviewed, AI reviewed, or human reviewed (and whether a person approved it). Reviews never block anything. Commit, verify, push and pull work the same either way. The flag records who has looked.

From the command line

> hs show head
#pu3px2eie3  2026-11-15 02:44  alice
    mul: reject negative multipliers
    tests: passed   review: unreviewed

  changed       calc/ops.py:mul   [1/1 passed]
      @@ -1,4 +1,7 @@
       def mul(a, b):
      +    """Multiply a by a non-negative integer b."""
      +    if b < 0:
      +        raise ValueError("b must be non-negative")
           total = 0
           for _ in range(b):
               total = add(total, a)
> hs review head approve -m "negative b now raises; test_mul passes"
Recorded your review of #pu3px2eie3: approved. Commit is now human approved.
> hs reviews
#pu3px2eie3  human approved            mul: reject negative multipliers
#myiw7fzhc3  unreviewed                Import the calc sample

hs show gives the line diff of every changed function, module code (imports, constants) and deleted code, each function's test summary, and the reviews so far. hs review takes approve, changes or comment. A summary (-m) is needed unless you approve. hs push ends with how much of what it pushed a person has reviewed.

Person or AI? A review recorded in a normal terminal counts as a person's. Run under an AI agent (Claude Code and others are detected), it counts as an AI review. HS_REVIEWER=human or ai overrides this. Agents review through MCP with hs_review, which always counts as an AI review.

In the browser

> hs ui
Review pages for calc: http://127.0.0.1:7421/ui/p/calc
(Ctrl+C to stop)

This opens review pages for your local database, much like GitHub's:

  • Commits: every commit with its test result and review flag, what is waiting for a person, uncommitted changes, and functions with failing tests.
  • A commit: a side-by-side-numbered diff per function, with its test summary (for example 18/20 passed), the reviews, and a form to approve, request changes or comment.
  • Tests: every function's result with a pass/fail bar, failing ones first.
  • A function: its code, each test's result on this code (with the pytest output when one fails), notes, context, callers and history.

The hub serves the same pages for its copy at http://<hub>:7420/ui, and also lists pushes with how much of each a person reviewed. Reviews travel both ways: a review made locally is sent to the hub straight away (or with the next push), and reviews made on the hub arrive with hs pull.

Where commits waiting for approval are listed is a setting: [review] approval = "both" (local, hub, both or off). On a shared hub, start it with --review-token <secret> so that only people you give the token to can record a person's review there.

7History and rollback

hs log shows commits. hs history shows every step, committed or not:

> hs history -n 4
* @14  2026-11-14 23:05  verify   failed: 3 tests, 3 failures
  @13  2026-11-14 23:05  commit   Experiment
  @12  2026-11-14 23:05  update   Experiment: subtract instead; stored calc/ops.py:add
  @11  2026-11-14 23:05  push     pushed main to origin
> hs rollback @11
Working state restored to @11 (push: pushed main to origin).
The state before the rollback is still in hs history.
> hs view calc/ops.py:add
# calc/ops.py:add  #uo6gamhvxd
def add(a, b):
    return a + b

The rollback is itself a step (@15 rollback back to @11), and the experiment is still at @12–@14. Rollback changes the working state, which you then commit as usual. To undo the rollback, roll back to @14. hs log calc/ops.py:mul shows one function's history, and hs diff --from head~1 --to head compares commits.

8Notes and context

Notes cover a range of lines and are kept beside the code, not in it. hs why records context: where a function came from, design decisions, and requests.

Added note fc90ad8a to calc/ops.py:mul lines 2-4
> hs why calc/ops.py:mul "Multiply by repeated addition so the sample has a call graph" --kind origin

10Working with a hub

Start a hub

> hshub create calc --root D:\hashstash-hub
> hshub serve --root D:\hashstash-hub --port 7420

The hub listens on 127.0.0.1 by default. To share it on your network, add --host 0.0.0.0, and --token <secret> so that only clients with HS_TOKEN=<secret> set can connect. Open http://localhost:7420/ to see the hosted projects.

Push

> hs remote add origin http://localhost:7420/calc
> hs verify
> hs push
Pushed main #b5dpcitcko to origin (16 objects uploaded).

Clone and pull

> hs clone http://localhost:7420/calc calc-bob
Cloned http://localhost:7420/calc into C:/…/calc-bob: fast-forward to #b5dpcitcko
> cd calc-bob
> hs pull
fast-forward to #c4n53okjgb (5 objects fetched, 1 hub locks)

Only missing objects are sent each way. After the import, the mul edit pushed 5 objects, not the whole project.

Who am I? Set your name with HS_AGENT (or --as <name> on any command). Commits, locks and history are recorded under it. Give every agent its own name.

11Locks

A lock reserves definitions for one agent. hs edit takes locks automatically, and hs commit releases them (--keep-locks keeps them). When the project has an origin remote, locks are taken on the hub, so they apply to everyone:

# bob
> hs lock calc/ops.py:Calculator.clear
Locked calc/ops.py:Calculator.clear until 2026-11-14 23:14
# alice
> hs lock calc/ops.py:Calculator.clear
hs: calc/ops.py:Calculator.clear is locked on the hub by bob
  • hs locks lists locks, and hs unlock <name> releases one. hs unlock --force breaks someone else's lock.
  • Locks expire after [locks] minutes unless renewed. Editing renews them.
  • The hub refuses any push that changes a definition someone else has locked.
  • HS_OFFLINE=1 skips the hub, for working without a connection.

12Publishing to git (nightly builds)

The hub can render a branch into a normal git repository and push it, for example to GitHub. Anyone can then clone, build and browse plain source files, and every published commit corresponds to a verified hashstash state.

  1. Add a [publish] section to the hub project's settings, D:\hashstash-hub\calc\.hs\config.toml: 
    [publish]
git_dir = "../calc-publish"                         # working copy, created on first use
remote  = "https://github.com/you/calc.git"         # or a local bare repo path
branch  = "nightly"
on_push = true                                      # publish after every accepted push
  2. Publish by hand at any time: 
    > hshub publish calc --root D:\hashstash-hub
{
  "changed": true,
  "commit": "dsardkmbte",
  "deleted": 0,
  "dir": "D:/hashstash-hub/calc/../calc-publish",
  "git_commit": "00b6b34",
  "pushed": "origin/nightly",
  "written": 3
}
    The git commit lists the hashstash commits since the last publish: 
    > git log -1 --format=%B nightly
hashstash publish #dsardkmbte (main)

- mul: reject negative multipliers (#dsardkmbte, alice)
- Import the calc sample (#t4vmgaayks, alice)
    A fresh clone of nightly holds the plain files, and pytest passes on them.
  3. Or once a night with Task Scheduler, instead of on_push: 
    > schtasks /Create /SC DAILY /ST 02:00 /TN "hashstash nightly calc" ^
    /TR "C:\Projects\hashstash\build\hshub.exe publish calc --root D:\hashstash-hub"
Use a separate branch. Publishing replaces every file on the target branch with the rendered tree. Point it at a branch like nightly, and merge into main on GitHub when you choose to release. Git needs credentials for the remote (Git Credential Manager handles this for GitHub).

For a single project without a hub, the same [publish] section in the project's own .hs/config.toml works with hs publish.

13Connecting AI agents (MCP)

Agents use the same functions through MCP. The tools describe themselves, so the agent needs no extra instructions.

Local project (stdio)

hs mcp serves the project found in or above the folder it starts in. With Claude Code, run this in the project folder:

> claude mcp add hashstash -- hs mcp

Or check a .mcp.json into the project:

{
  "mcpServers": {
    "hashstash": { "command": "hs", "args": ["mcp"], "env": { "HS_AGENT": "claude" } }
  }
}

Directly on the hub (HTTP)

For agents without a local copy:

> claude mcp add --transport http hashstash-hub http://localhost:7420/mcp/calc

14Settings

Each project has .hs/config.toml. These are the defaults hs init writes:

[project]
name = "calc"

[user]
# author = "Your Name"

[size]
warn_lines = 60   # warn when a definition is longer than this
max_lines  = 0    # refuse longer definitions (0 = never refuse)

[locks]
minutes = 15      # a lock expires unless renewed within this time

[tests]
require = "warn"  # every function/method needs linked test cases: off | warn | block
# exempt = ["__repr__", "_*"]   # short names that need no tests
python = "python -m pytest -q {tests}"   # how hs verify runs Python tests
impact_depth = 3  # verify also runs the tests of callers up to this many levels away (0 = off)

[history]
keep = 500        # lifecycle steps kept per branch for rollback (0 = keep all)

[review]
approval = "both" # where commits waiting for a person are listed: local | hub | both | off

[import]
# ignore = ["*.min.js", "data/**"]

[publish]
# git_dir = "../myproject-git"
# remote  = "origin"
# branch  = "main"
# on_push = false

16When something is refused

MessageWhat to do
head … is not verifiedRun hs verify, then push again.
head … is failing verificationFix the failing tests (hs verify --json shows pytest output), or hs rollback.
… is locked on the hub by bobWait, ask bob, or let the lock expire. hs locks shows when.
the hub's main has commits you don't have: pull firstSomeone pushed first. Run hs pull, verify, and push again.
you have uncommitted changes: commit them, then pullCommit (or roll back) first, then pull.
your main and the hub's have diverged; merging is not supported yetYou and someone else both committed. Merging is the next feature. Until then, roll back to the last pulled state, pull, and redo your edit on top.
… changed since it was opened on updateSomeone else changed the function after you opened it. Run hs edit again to get the current version.
hub … unreachableStart hshub serve, or check the remote URL with hs remote add origin <url>.
A test passes locally but fails in verifyVerify runs from the rendered tree, from the project root described in section 5. Check that the test doesn't depend on files that weren't imported.

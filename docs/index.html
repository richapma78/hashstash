hashstash
Concept Manual Design notes

Version control for AI/SI agentic coding

Version control that stores functions, not files.

hashstash keeps your code as a database of definitions: every function, method and class, each with its own hash, history, tests, notes and lock. Ordinary source files are generated from it whenever you need them, ready to build, run or push to GitHub. It works with Python and C/C++.

Function-level history

Commits, diffs, blame and rollback per definition, with line-by-line diffs inside each one.

Built for agents

An MCP server exposes everything as tools, so an AI agent can browse, lock, edit, test and push without a skill file.

Tests travel with code

Every function links to the tests written for it. Pushes must pass them, including the tests of anything that calls it.

Plain files out

Rendering gives byte-identical source files, so git, compilers and GitHub never notice anything unusual.

1Files go in, definitions come out

hs import parses each file with tree-sitter and stores every definition as its own object. The text between definitions (imports, comments, module code) is kept too, so nothing is lost.

Nested definitions (methods inside a class) are their own objects too. The class keeps a reference to each.

2Two identities for every definition

Each definition has a content hash, which changes with every edit, and a lineage ID, which never changes, even through renames. Tests, notes, locks and history attach to the lineage, so they follow the function wherever it goes.

The same content always hashes the same, so identical code is stored once, and sync only sends hashes the other side doesn't already have. (Versions 1 and 2 are real hashes from the manual's walkthrough; the rename and the lineage IDs are illustrative.)

3Rendering back to files

Each file is stored as an ordered list of text and definition references: its crumbtrail. hs render walks it and writes the file back byte for byte, comments, blank lines and line endings included. Tested on the whole Python standard library (12,893 files) and on hashstash's own C/C++ sources, with zero mismatches.

4The working loop

The code lives in the store, not in files. Checking out a function means locking it and opening it in a scratch file. You edit there, then store it back. Agents do the same through MCP tools.

5Every function has tests, and pushes must pass them

Tests are linked to the definitions they exercise. One function can have many tests, and methods count too. Import links tests automatically from the call graph, and a function with no tests gets a warning (or blocks, if you choose). Before a push, hs verify renders the code and runs:

  • the tests linked to everything the hub hasn't seen yet;
  • the tests of everything that calls those definitions, found through the call graph (up to 3 levels by default).
Each function also gets a suite hash (its hash plus its tests' hashes), so test results are tied to the exact code they checked.

6Notes and context live beside the code

Comments on a line range are stored next to a definition, not inside it, so they never clutter the code or cause merge noise. Regions can overlap, and they move when lines are inserted above them. Each definition also keeps its context: the original request, design snippets and the reason for every change.

Real output from the manual's walkthrough: hs context calc/ops.py:mul shows the note at lines 5–7 after the edit.

7History never loses work

Besides commits, hashstash records a lifecycle history of every step: import, update, commit, verify, push, note. Rolling back restores an earlier state by adding a new step, so the state you rolled back from is still there to return to. [history] keep sets how many steps are kept.

8The hub: a GitHub for hashstash

Each project has a local store. hshub is the shared server, on your machine or in the cloud. It hosts many projects, takes pushes and pulls of hash deltas, runs the shared lock service, serves MCP over HTTP, and can publish any branch to an ordinary git repository.

Built to scale up

The hub talks to storage only through two interfaces, so the SQLite backend used today can be replaced without touching the protocol. This follows the way large code hosts scale:

9Made for AI agents

Everything a person can do with hs, an agent can do through MCP: 33 self-describing tools, from hs_find and hs_graph to hs_edit_def, hs_verify and hs_push.

Small units

Agents read and change one function at a time, not whole files. Overlong definitions get a warning to split them.

Locks

An agent locks what it edits. Other agents are refused, locally and on the hub.

Reasons recorded

Every MCP edit needs a reason, which becomes part of the function's context history.

Graph queries

Callers, callees, impact, paths, unused code and cycles, answered from the index in one call.

10Who has looked: review flags and review pages

Agents commit a lot of code, so every commit records who reviewed it. Approval is never required; the flag simply shows, on your machine and on the hub alike, whether a commit was only checked by an AI or a person looked too.

After committing, an agent gets back the exact line diff it stored, checks it, and records an AI review. A person can approve later in the browser.

Line diffs per function

hs show, MCP hs_show and the pages show every changed function, module code and deleted code line by line.

Test results per function

"18/20 passed, 2 failed" beside each function, so you only open the tests that matter.

Review pages

hs ui for your local copy, /ui on the hub: commits, pushes, diffs, tests, and a form to approve or request changes.

You choose where

[review] approval lists commits waiting for a person locally, on the hub, both, or nowhere.
